# Onboard Customer Portal (backend-only)

Get a customer's forked copy of Assets Hub Spark booting locally, with a
correctly reported auth state and real search working against their own
Adobe Content Hub environment — and make sure every file in the repo that
currently identifies the *upstream template* (its GitHub org/repo,
Cloudflare worker/account/resource ids, domain) instead identifies the
*customer's own fork*. This skill never creates cloud resources itself,
never deploys, and never stores or transmits real secret values — it edits
local, gitignored files, writes non-secret resource identifiers the
customer supplies, and tells the customer where to paste actual secrets
themselves.

**Out of scope, on purpose:** branding, logo/favicon, DA-authored nav/footer/
homepage content, or any visual theming. That work is driven by a separate
effort (e.g. the `excat:*` skills, invoked independently by the customer or a
different skill) and is never triggered from here. If the customer asks for
that in the same conversation, do the backend steps below, then tell them
plainly that branding is a separate next step — don't attempt it.

**Never hardcode this template's own identity.** Nothing in this skill's
own logic should assume the literal strings `assethub-spark`, `aem-showcase`,
`spark-eds`, `spark.aem.media`, or any other value found in the inventory
below. Always *derive* the current ("old") values by reading the fork's own
files at run time, and *derive* the new values from what the customer
supplies. This is what lets the skill work correctly no matter what the
upstream template happens to be named by the time it's run.

## State file

All progress is tracked in `.internal/onboarding-state.json` (gitignored via
the existing `.internal` entry in `.gitignore` — do not add a new ignore
rule). This file is the resumability mechanism: if the customer leaves
mid-flow (e.g. waiting days on their Adobe rep for Content Hub credentials,
or on their own team to provision Cloudflare resources) and comes back in a
new session, re-read this file first and resume at the first non-`done` step
rather than re-asking already-answered questions or re-running
already-verified checks.

It is also the handoff point for any future, separate onboarding skill (e.g.
a branding/UI skill). This skill only ever reads/writes its own
`phases["backend-onboarding"]` key. It must never assume other `phases.*`
keys exist, and must never write into them.

Schema:

```json
{
  "schemaVersion": 1,
  "customer": {
    "name": null,
    "githubOrg": null,
    "githubRepo": null,
    "aemEnvId": null,
    "authBypassActive": null
  },
  "phases": {
    "backend-onboarding": {
      "status": "in_progress",
      "skill": "onboard-customer-portal",
      "lastUpdated": null,
      "steps": {
        "node-version-check": "pending",
        "fork-identity-resolved": "pending",
        "code-sync-verified": "pending",
        "intake-file-generated": "pending",
        "content-hub-creds-collected": "pending",
        "repo-identity-rename-applied": "pending",
        "auth-bypass-checked": "pending",
        "local-env-configured": "pending",
        "boot-verified": "pending",
        "deploy-readiness-noted": "pending"
      }
    }
  }
}
```

Step values are one of `pending`, `done`, or `blocked` (blocked = waiting on
something external, e.g. the customer fetching credentials or provisioning
Cloudflare resources). Update `lastUpdated` and the relevant step every time
you complete or block on a step. Set
`phases["backend-onboarding"].status` to `"done"` only when every step is
`done` (`deploy-readiness-noted` counts as `done` once reported — it's
informational, not a blocking gate on its own).

If the file doesn't exist, create it with the schema above before doing
anything else. If it exists, read it and jump to the first non-`done` step —
do not redo completed steps or re-ask questions whose answers are already
recorded under `customer`.

## Companion file: customer-config intake

`.internal/customer-config.json` (also gitignored, same convention) holds
non-secret Cloudflare identity/resource values the customer must look up
themselves — values that aren't practical to collect one-at-a-time through
chat because most require running a command or checking a dashboard first.
Generated by step 4 below; described fully there.

This file is distinct from `cloudflare/.secrets`: nothing in
`customer-config.json` is a secret (these are identifiers, the same kind of
thing visible in a dashboard URL — an account id or a KV namespace id is not
a credential). The skill may read this file directly and write its values
into `wrangler.toml` and other files. Real secrets (Content Hub client
secret, any Entra client secret) never go in this file — those stay in
`cloudflare/.secrets`, which the skill never reads back.

## Steps

### 1. Node version check (`node-version-check`)

Read `.nvmrc` at the repo root for the required Node major version. Run
`node --version` and compare. If it doesn't match, stop and tell the
customer to switch (e.g. `nvm use`) before continuing — do not attempt to
proceed on a mismatched version, since `npm install` will emit engine
warnings and dependencies (wrangler, vite, etc.) may misbehave silently.

Once matched: if `cloudflare/node_modules` is missing, run `npm install` at
the repo root (this recurses into `cloudflare/` via the `postinstall`
script). Mark step `done`.

### 2. Fork identity resolution (`fork-identity-resolved`)

Do not ask the customer for their GitHub org/repo — derive it from the fork
itself:

```
git remote get-url origin
```

Parse `{org}/{repo}` from the URL. Write these into `customer.githubOrg` /
`customer.githubRepo` in the state file. Mark step `done`.

If there is no `origin` remote (e.g. repo was copied, not cloned), ask the
customer directly for their GitHub org and repo name instead, and proceed the
same way.

### 3. AEM Code Sync verification (`code-sync-verified`)

Using the org/repo from step 2, construct the expected Helix preview URL:

```
https://main--{repo}--{org}.aem.page
```

Fetch it (e.g. via `curl -sI` or a WebFetch). Determine the result:

- **Real content / 200** → Code Sync is installed and working. Mark step
  `done`.
- **404 / "site not found" / similar** → Code Sync is not installed yet.
  Explain to the customer, in plain terms, that this is a required one-time
  GitHub-side step they must do themselves (the agent cannot install a
  GitHub App on their org): install the AEM Code Sync GitHub App on their
  forked repository. Point them to the aem.live documentation for exact
  steps (do not guess the App's install URL — look it up if needed rather
  than fabricate it). Mark step `blocked`, explain you'll re-check once
  they've done it, and stop here for this session if they need to go do it
  now.

Do not proceed past this step on an unverified assumption — a customer whose
Code Sync isn't installed will silently see Adobe's own demo content via the
`aem up` fallback proxy instead of their own, which is confusing and wastes
the rest of the flow.

### 4. Intake file generation (`intake-file-generated`)

Several values needed later (step 6) require the customer to run a command
or look something up in their own Cloudflare account first — they can't
usefully be answered inline in chat one at a time. Generate
`.internal/customer-config.json` pre-populated with these fields, each
`null` until filled in, plus how to get each one:

```json
{
  "cloudflareAccountId": null,
  "workersDevSubdomain": null,
  "workerName": null,
  "productionDomain": null,
  "kvNamespaceId": null,
  "d1DatabaseIds": {
    "userLogins": null,
    "auditEvents": null,
    "searchEvents": null
  },
  "secretsStoreId": null
}
```

Tell the customer, for each field, exactly how to get the value — prefer the
`wrangler` CLI wherever it gives an unambiguous answer (they already have it
installed for local dev), fall back to a dashboard path only where no CLI
getter exists:

- `cloudflareAccountId` — run `wrangler whoami` (or Cloudflare dashboard:
  Workers & Pages → Overview → Account Details card).
- `workersDevSubdomain` — dashboard only, no CLI getter: Workers & Pages →
  click **Change** next to "Your subdomain". If they've never set one, they
  need to set it now — it's an account-level setting, not per-worker.
- `workerName` — their own free choice; suggest a default derived from the
  repo name (e.g. `{repo}` or `{repo}-portal`) but let them override.
- `productionDomain` — optional. Their own DNS zone already added to
  Cloudflare, if they have one. They may leave this blank and stay on
  `*.workers.dev` only for now — note that if left blank, later steps use
  `*.workers.dev` URLs wherever a production domain would otherwise go.
- `kvNamespaceId` — run `wrangler kv namespace create AUTH_TOKENS`; the id is
  in the command's output.
- `d1DatabaseIds.userLogins` / `.auditEvents` / `.searchEvents` — run
  `wrangler d1 create <name>` **once per binding**, three separate times with
  three different names; each prints its own `database_id`. These must end
  up as three distinct ids — do not let the customer reuse one id for all
  three (that's the exact cross-contamination risk the upstream template
  itself has, don't propagate it into the fork).
- `secretsStoreId` — run `wrangler secrets-store store create`; the id is in
  the command's output.

Tell the customer to fill this file in at their own pace — this can take a
while if they need to provision fresh Cloudflare resources — and to let you
know when it's done. Mark step `blocked` until they confirm, then re-read
the file, confirm every field is non-null (except `productionDomain` if
intentionally skipped), and mark `done`.

### 5. Content Hub credential collection (`content-hub-creds-collected`)

Ask the customer for:

- **`AEM_ENV_ID`** — their AEM Program + Environment ID, format `pXXXX-eYYYY`.
- **Content Hub OAuth Server-to-Server credentials** — client ID and client
  secret, from an Adobe Developer Console project with access to that
  delivery environment's Dynamic Media / Content Hub API.

These come from Adobe Developer Console, not a Cloudflare lookup, so they're
fine to ask directly in chat rather than via the intake file — but never ask
the customer to paste the secret values themselves into the chat. Instead:

1. Tell them to create `cloudflare/.secrets` (gitignored) from the template
   documented in `cloudflare/README.md` / root `README.md`, if it doesn't
   exist yet.
2. Tell them exactly which two lines to add/fill in themselves:
   `SPARK_DM_CLIENT_ID="..."` and `SPARK_DM_CLIENT_SECRET="..."`.
3. Confirm with them that they've done it (yes/no) — do not read the file's
   contents yourself to "verify"; that would mean handling the secret value
   directly, which this skill must not do.

Also check whether `cloudflare/.secrets` has a `SPARK_COOKIE_SECRET` line —
required by `cloudflare/src/auth.js`'s `REQUIRED_ENV_VARS` regardless of
auth-bypass state. If missing, generate one locally with
`openssl rand -base64 32` and have the customer add that generated value
themselves — this one isn't a customer-supplied secret, just a value that
needs to exist.

Write only the non-secret `aemEnvId` into `customer.aemEnvId` in the state
file. Mark step `done` once the customer confirms all three lines are in
place and `AEM_ENV_ID` is recorded.

### 6. Repo identity rename (`repo-identity-rename-applied`)

This is the step that repoints every file in the repo that currently
identifies the upstream template instead of this customer's fork. Do this as
one bulk, previewed, single-confirmation pass — not file-by-file
confirmations — since every change here is a mechanical substitution of
values already known by this point, not a judgment call.

**Gather the substitution map** (old → new), reading old values live from
the files rather than assuming them:

- GitHub org/repo: read the *current* `HELIX_ORIGIN` value out of
  `cloudflare/wrangler.toml` (or `local.sh`'s `AEM_PAGES_URL` default) to
  find the old `{repo}--{org}` pair → new value is `customer.githubRepo` /
  `customer.githubOrg` from step 2.
- Cloudflare worker name: read the current `name` field in
  `cloudflare/wrangler.toml` → new value is `workerName` from the intake
  file.
- Cloudflare account id: read the current `account_id` in
  `cloudflare/wrangler.toml` → new value is `cloudflareAccountId` from the
  intake file.
- Production domain / workers.dev subdomain: read the current route/domain
  literals (search the repo for the domain string used in
  `cloudflare/wrangler.toml`'s `routes`) → new value is `productionDomain`
  and/or `workersDevSubdomain` from the intake file, per field.
- KV namespace id, three D1 database ids, Secrets Store id: read the current
  ids in `cloudflare/wrangler.toml` → new values from the intake file's
  matching fields.
- `AEM_ENV_ID`: read the current value in `cloudflare/wrangler.toml` → new
  value is `customer.aemEnvId` from step 5.

**Files to update** — search the repo for the old values found above (do not
assume this exact list is complete if the repo has changed since this skill
was written — always re-derive by searching, this list is a starting point
based on a code audit, not a guarantee):

- Functional/CI: `cloudflare/wrangler.toml`, `cloudflare/scripts/deploy.sh`,
  `.github/workflows/build.yaml`, `.github/workflows/release.yaml`,
  `local.sh`, `package.json`, `cloudflare/package.json`,
  `sonar-project.properties`, `cloudflare/src/index.js` (CORS
  `allowedOrigins` — security-relevant: the fork's real frontend origin
  needs to be in this allowlist or the browser rejects its own app's
  requests), `cloudflare/src/user.js` (the `liveHosts` array — 
  security/access-relevant: if the fork's real production host isn't listed
  here, every request to it is treated as a preview request and requires
  the `preview` permission, effectively locking out normal users),
  `cloudflare/src/api/notifications.js` (default from-email),
  `cloudflare/src/api/analytics.js` (fallback analytics account id — two
  occurrences), `tests/shared/env.js`, `tests/integration/test-public-urls.sh`.
- Documentation (same substitution values, same pass): `README.md`,
  `ARCHITECTURE.md`, `cloudflare/README.md`, `cloudflare/NOTES.md`,
  `.cursor/rules/aem.mdc`, `.github/pull_request_template.md`,
  `docs/api/API-SECURITY-REVIEW.md`, `docs/authoring/getting-started.md`,
  `docs/authoring/localization.md`,
  `docs/administering/permission-configuration.md`,
  `docs/authoring/blocks/*.md`, `docs/da-content/create-docs.py`,
  `docs/da-content/create-sheets.py`, `tests/integration/README.md`,
  `tests/integration/setup/auth.js`, `tests/integration/test-runner.test.js`,
  `tests/authz/helpers.js`.
- **Do not touch** `cloudflare/src/origin/__tests__/dm-analytics-search-type.test.js`
  — its domain-looking strings are arbitrary test fixture input to a
  referer-parsing function that only inspects the URL path; changing them
  would be pure churn with no behavior difference.
- `blocks/search-results/components/adobe-pdf-viewer.js` has its own,
  separate placeholder (`'REPLACE_WITH_SPARK_PDF_EMBED_CLIENT_ID'`) keyed by
  production domain — this needs the customer's own Adobe PDF Embed API
  client id, a distinct credential from anything else collected so far, not
  derivable from the rename substitution map. Note it in the completion
  report as a known follow-up rather than blocking on it here.

**Process:** build the full list of (file, line, old value, new value)
changes, show the complete diff/preview to the customer, get one
confirmation, then apply all of them. After renaming `package.json`
(root) and `cloudflare/package.json`, regenerate
`package-lock.json`/`cloudflare/package-lock.json` by running `npm install`
— do not hand-edit the lockfiles.

Mark step `done` once applied and confirmed.

### 7. Auth-bypass check (`auth-bypass-checked`)

Read `cloudflare/src/auth.js` and check whether the `DISABLE_AUTHENTICATION`
bypass block inside `withAuthentication` is active code or commented out.

If it's commented out (as of this writing, it is — lines ~161-172): tell the
customer plainly that setting `DISABLE_AUTHENTICATION=true` will **not**
actually disable login today. Every route still requires a valid session
cookie via the normal Entra flow; the env var currently only affects one
special case on the `/public/welcome` page. Give them the exact file/line
location. Ask whether they want to:

- Proceed anyway with real auth still required locally (they'll need to
  complete a real Microsoft Entra login once against whatever
  `MICROSOFT_ENTRA_TENANT_ID`/`CLIENT_ID` is currently configured — likely
  still the upstream template's own placeholder values unless already
  replaced in step 6, in which case they'd need their own real Entra app
  registration now rather than later — see step 10), or
- Pause here until they/their engineering team restores that bypass block
  themselves.

Do not edit `auth.js` yourself — this is a code change, not a config value,
and outside this skill's job. Record `customer.authBypassActive` as `true`
or `false` in the state file based on what you found (not based on what the
customer wishes were true), and mark this step `done` either way — "done"
here means "the true state is now known and recorded," not "the bypass
works."

Still set `DISABLE_AUTHENTICATION=true` in the local env regardless of the
outcome (harmless either way, and immediately correct if/when the block is
restored).

### 8. Local environment configuration (`local-env-configured`)

`wrangler.toml`'s `HELIX_ORIGIN` value is not consulted by `local.sh` for
local dev (it always points the local Cloudflare worker at the
locally-running `aem up` server instead) — but it matters for CI/deploy,
which step 6 already corrected.

Set these for the `npm run dev` invocation (export before running, or via a
local `.env` file per the "Environment variables supported by `npm run dev`"
table in the root `README.md` — never commit `.env`):

- `AEM_PAGES_URL` = `https://main--{repo}--{org}.aem.page` (the customer's
  own fork's Helix preview, from steps 2/3).
- `AEM_ENV_ID` = the value collected in step 5.
- `DISABLE_AUTHENTICATION` = `true`.

Mark step `done`.

### 9. Boot verification (`boot-verified`)

Run `npm run dev` with the environment from step 8. Wait for both the AEM
dev server and the Cloudflare worker dev server to report ready (the script
itself polls and prints readiness — watch for its own "Ready on
http://localhost:{port}" line, don't guess a fixed wait time).

Once up, verify, in order:

1. **The server is serving this repo's own local files**, not a stale or
   unrelated cached directory — check that a distinctive string from a
   local file (e.g. something specific in `styles/styles.css` or a block
   file) actually appears in the served output. Don't assume a 200 response
   means the right content is being served.
2. Auth-redirect behavior matches what step 7 recorded: if
   `authBypassActive` is `false`, expect and accept a real Entra login
   prompt as correct current behavior, not a failure. If somehow `true`
   (bypass restored), confirm no login prompt appears.
3. A real search request against the portal returns results sourced from
   the customer's own Content Hub environment — not an auth error, and not
   obviously-upstream-demo content.

If search fails, check the most likely causes in order: wrong/missing
`SPARK_DM_CLIENT_ID`/`SECRET` in `cloudflare/.secrets`, wrong `AEM_ENV_ID`,
or the Content Hub technical account lacking access to that delivery
environment. Report the specific failure back to the customer rather than
guessing further fixes.

Mark step `done` once verified.

### 10. Deploy readiness note (`deploy-readiness-noted`)

Informational only — this skill never deploys. Once local dev is verified,
tell the customer plainly what's still needed before any real deploy:

- **A real Microsoft Entra app registration**, independent of the
  auth-bypass gap: `cloudflare/src/auth.js`'s `REQUIRED_ENV_VARS` hard-blocks
  `/auth/*` (503) if `MICROSOFT_ENTRA_TENANT_ID`/`CLIENT_ID` are missing —
  this check fires regardless of `DISABLE_AUTHENTICATION`, and there is no
  bypass-in-production path (the same commented-out block applies wherever
  `withAuthentication` runs, not just locally). Concretely, their IT admin
  needs to:
  1. Go to entra.microsoft.com (or the Entra blade in portal.azure.com) →
     **App registrations → New registration**.
  2. Register the redirect URI under the **Single-page application**
     platform (not "Web") — this matches the code's flow (redirect to
     `/authorize`, validate the returned `id_token` via JWKS, no client
     secret involved).
  3. Copy the **Application (client) ID** and **Directory (tenant) ID** from
     the app's Overview page → these are `MICROSOFT_ENTRA_CLIENT_ID` /
     `MICROSOFT_ENTRA_TENANT_ID`. No extra API permission setup is needed for
     basic sign-in. No premium Entra license tier is required — this works
     on the free tier bundled with any Microsoft 365/Azure subscription.
  4. If they also want SMTP email sending (per `cloudflare/README.md`), the
     *same* app registration can additionally hold a **Web** platform
     config (confidential client, with a client secret) for that — one app
     registration, two platform entries, not two separate registrations.
- **The auth-bypass gap itself**: either it stays unresolved and every
  deployed environment requires real login (which then requires the Entra
  registration above), or the customer's engineering team restores the
  commented-out bypass block first — that's their call, not something this
  skill decides.
- **Any intake-file fields left blank** (e.g. `productionDomain` if they
  deferred to `*.workers.dev` only) — note which ones, since deploying to a
  real custom domain later will need them filled in and step 6 re-run for
  those specific values.

Mark step `done` once reported, and set
`phases["backend-onboarding"].status` to `"done"`.

## Completion report

Summarize plainly:

- What's now configured and verified (local dev boots, real search live
  against their Content Hub).
- Every identity value that was renamed and where (worker name, account id,
  domain/subdomain, KV/D1/Secrets-Store ids, GitHub org/repo).
- The true current auth-bypass state (`authBypassActive`) and what that
  means for local use today.
- The deploy checklist from step 10 (Entra registration, auth-bypass
  resolution, any deferred intake-file fields).
- The known PDF-preview gap (`adobe-pdf-viewer.js` placeholder client id) —
  not blocking, search doesn't depend on it.
- That this covers backend/config only — branding, logo, nav, footer, and
  any other visual/content work is a separate step, not part of this skill,
  and must be requested/invoked separately.
- The state file and intake file locations, in case they want to inspect
  them or a future onboarding step needs them.
