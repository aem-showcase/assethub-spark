  The skill is architected as one fixed, all-or-nothing sequence. There's no
  partial/branding-only mode, and several places explicitly forbid the "just
  change the icon/color" shape you're describing.

  Why it can't do a partial demo today

  1. The sequence is declared as the single source of truth, 1:1 with state.
  SKILL.md:37-64 — every demo is steps 1→6 in order, mirrored by the steps
  object. intent has exactly one legal value:

  ▎ "Every demo is full — there is no other intent value." (SKILL.md:109)

  2. The workflow explicitly bans the "branding-only" question.
  SKILL.md:186-188:

  ▎ "Never ask a 'full vs. branding-only' question either — every demo always 
  ▎ includes assets; the only open questions are where the assets come from and 
  ▎ when enrichment runs."

  So even "just change the color" gets routed into: confirm → branch → mandatory
  DA content copy → rebrand → publish → PR → assets → collections.

  3. The one hard gate makes an icon/color change the maximum-cost path, not 
  minimum.
  SKILL.md:66-70 and Step 4's gate (SKILL.md:319): you may not touch a single 
  styling file until a branch exists and the entire site's DA content has been
  copied into /companies/<company>. Step 3 is labeled "MANDATORY — never
  skipped, deferred, or assumed away" (SKILL.md:305-311). A user who just wants
  a recolored icon still pays for: a git worktree, a full DA content copy, a
  publish of every copied path (I7), and an open PR.

  4. The lightest thing the skill offers isn't light.
  The closest to "partial" is assetsEnrichNow=false (defer enrichment) — but
  that still requires branch + full DA copy + rebrand + publish + PR
  (SKILL.md:235, I4). It defers the back half, never the front half. There is no
  way to defer/skip the DA copy or the PR.

  5. Design tooling only enters through the gate.
  excat-complete-design-expert (the thing that actually does color/logo/icon
  work) is only invokable inside Step 4, after Steps 2+3 are done
  (SKILL.md:66-70, SKILL.md:319, docs/invariants.md I3). There's no standalone
  "style this one thing" entry point in this skill.

  What does exist for small styling tasks

  If the goal is genuinely "demo the agent's capability by changing an icon or
  color," that's what the excat design skills are for, standalone — outside
  rebrand-portal:

  - excat:excat-complete-design-expert — its description explicitly supports
    "individual block styling" and "site design only," triggered by "style the
    blocks," "apply styling," or naming a specific block. This is the granular,
    no-PR-no-DA-copy path.
  - excat:excat-block-design-expert (agent) — migrate/restyle a single block's
    visual design.
  - excat:excat-visual-critique — "critique this," "fix block styling," "match
    original block."

  These do the small visual change without the branch/DA-copy/publish/PR
  machinery rebrand-portal forces.

  Bottom line

  rebrand-portal = "produce a shareable rebranded demo portal, end to end." It
  deliberately refuses to be a partial tool — the invariants treat "skip the DA
  copy / skip the PR" as the exact failure mode it exists to prevent
  (SKILL.md:66-70).

  For "just change the icon or color to demo the capability," point users at the
  excat design skills instead — they're built for single-block / design-only
  scope.

  What changed in my thinking

  This isn't "full vs. one quick lane" — it's intent-driven task composition.
  Capture which outcomes the user asked for along independent axes, run those,
  skip the rest. Full demo = all axes.

  The four outcome axes:
  - A. Look — recolor / swap logo+icon / restyle a block (excat; source URL is
    the style source, not a scope signal)
  - B. Content — page-copy rewrite
  - C. Assets — upload + enrich + landing cards (→ auto-follows into D)
  - D. Collections — depends on C

  Your two corrections, baked in:
  1. "Change my portal's color using brand.com" → A only. The word "portal"
     names the artifact, the URL is the palette source — neither means full
     scope. The router explicitly must not widen on either.
  2. "Just upload and enrich my assets" → C (+D). Assets are a standalone axis,
     not always coupled to rebrand.

  The shared foundation stays mandatory for every subset — branch + full DA copy
  + config.js scope + publish + open PR. Partial = a smaller change-set on the
  same foundation, never a smaller foundation.

  The one real blocker I found (§4 axis C, §9-Q1)

  An assets-only run trips a wall: both the Step 5 doc preflight and the
  guard-step5-verify-gate.sh hook require verify.mjs rebrand checks (residue,
  icon-render, …) to PASS before enrich-assets.js runs. But an assets-only run
  never rebrands — so the old brand's residue is expected, those checks would
  FAIL, and the hook would block enrichment forever.

  My recommended fix (C1): make verify.mjs --write-report intent-aware — when
  the run's axes exclude look, mark those A-only checks pass:true, reason:"n/a".
  The hook itself needs no change (it just reads the report honestly). This is
  the single change that touches a script + a doc gate; everything else is
  router + docs.
